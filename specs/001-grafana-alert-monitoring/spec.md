# Feature Specification: 疑似設備アラート監視システム

**Feature Branch**: `001-grafana-alert-monitoring`  
**Created**: 2026-04-25  
**Status**: Draft

---

## 1. はじめに

本ドキュメントは、AWS 上に構築する「疑似設備アラート監視システム」の要件定義書である。

Amazon Managed Grafana の学習・検証を主目的とした個人検証用の軽量システムであり、商用本番システムの正式な要件定義ではない。後続工程（仕様書・タスク書の作成 → Claude Code による実装）のインプットとして使用する。

実装担当者（Claude Code）が迷わない粒度で要件・スコープ・非機能・制約・受け入れ条件を整理する。

---

## 2. 背景

実案件で Amazon Managed Grafana を利用する予定があるが、利用経験がないため、個人の AWS 環境で小規模な検証システムを構築する。

単に Grafana の画面操作を学ぶだけでなく、AWS 上の業務システムにおける以下の監視・可視化手法を理解することを目的とする。

- API Gateway のリクエスト状況の監視
- Lambda の実行状況の監視
- DynamoDB のデータ保存状況の確認
- CloudWatch Logs / Metrics の活用
- Amazon Managed Grafana によるダッシュボード作成
- エラー・アラート件数の可視化
- 実案件に近い設備アラート監視の基本構成の習得

---

## 3. 目的

1. Amazon Managed Grafana の基本操作を理解する
2. CloudWatch をデータソースとして Grafana に連携する手順を習得する
3. API Gateway / Lambda / DynamoDB のメトリクスを Grafana で可視化できるようにする
4. 疑似的な設備アラートを受信・保存・可視化する一連の流れを構築する
5. 実案件での設備監視ダッシュボード設計に活かせる知見を得る
6. 可能な限り低コストで短時間（2 時間以内）に検証できる構成にする

---

## 4. システム概要

### 4.1 システム名

疑似設備アラート監視システム

### 4.2 システム種別

個人学習・技術検証用 AWS クラウドシステム

### 4.3 構成コンポーネント

| コンポーネント | 役割 |
|---|---|
| API Gateway | 疑似アラート受信エンドポイント |
| Lambda | リクエスト検証・データ保存処理 |
| DynamoDB | アラートデータ永続化 |
| CloudWatch Logs | Lambda 実行ログの収集 |
| CloudWatch Metrics | AWS サービス標準メトリクスの収集 |
| Amazon Managed Grafana | ダッシュボード可視化・アラートルール設定 |

### 4.4 処理フロー

```
[検証者]
   ↓ HTTP POST（疑似アラートデータ）
[API Gateway]
   ↓ Lambda 呼び出し
[Lambda]
   ├─ 入力値検証
   ├─→ [DynamoDB] アラートレコード保存
   └─→ [CloudWatch Logs] 処理ログ出力

[CloudWatch Metrics] ← AWS サービス標準メトリクス自動収集

[Amazon Managed Grafana]
   └─→ CloudWatch をデータソースとして参照
       → ダッシュボード可視化・アラートルール設定
```

### 4.5 AWS リージョン

東京リージョン（ap-northeast-1）を優先とする。

## 6. 前提条件

- 個人の AWS アカウントで構築する
- 検証時間は最大 2 時間程度を想定する
- 検証後は作成した AWS リソースをすべて削除する
- Amazon Managed Grafana の最低利用料金（約 9 USD）は許容する
- その他のリソース（API Gateway / Lambda / DynamoDB / CloudWatch）は無料枠または低料金に抑える
- 本番利用は想定しない
- 実案件に応用できる構成・設計思想を採用する
- IaC や詳細な実装方式は後続の仕様書・タスク書で整理する
- AWS サービスの詳細な実装手順は後続工程で定義する

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 疑似アラート送受信・保存の確認（Priority: P1）

検証者が HTTP クライアント（curl 等）を使って API エンドポイントに疑似設備アラートを POST し、データが正しく保存され、ログが出力されることを確認する。

**Why this priority**: システムの中核機能であり、データパイプライン全体（受信 → 検証 → 保存 → ログ出力）が機能することを最初に確認する必要がある。

**Independent Test**: API エンドポイントに JSON データを POST し、データストアにレコードが存在することとログ管理サービスにログが出力されることを確認できれば、この機能単体で完結する。

**Acceptance Scenarios**:

1. **Given** システムが起動済みの状態で、**When** 全必須フィールドを含む正常な JSON ボディを POST すると、**Then** HTTP 200 が返却され、データストアにアラートレコードが保存される
2. **Given** システムが起動済みの状態で、**When** 必須フィールド（alertId / facilityId / severity 等）が欠けた JSON を POST すると、**Then** HTTP 400 エラーが返却される
3. **Given** システムが起動済みの状態で、**When** severity に "critical" / "warning" / "info" 以外の値を送ると、**Then** HTTP 400 エラーが返却される
4. **Given** 既存の alertId と同一の alertId を持つリクエストを POST すると、**Then** 既存レコードが上書き更新される（upsert 動作）
5. **Given** Lambda が処理を実行した際、**When** 正常終了・異常終了いずれの場合も、**Then** ログ管理サービスに処理結果ログが出力される

---

### User Story 2 - Grafana ダッシュボードによるメトリクス可視化（Priority: P2）

検証者が Amazon Managed Grafana にアクセスし、CloudWatch を通じて API Gateway / Lambda / DynamoDB のメトリクスおよび疑似アラート件数をダッシュボードで確認する。

**Why this priority**: 本検証の主目的である Grafana 操作習得と可視化設計の理解に直結する。

**Independent Test**: Grafana の CloudWatch データソース設定が完了し、ダッシュボードに少なくとも 1 件のパネルにデータが表示されれば最低限の可視化機能として確認完了とみなせる。

**Acceptance Scenarios**:

1. **Given** Grafana が起動済みで CloudWatch データソースが設定された状態で、**When** ダッシュボードを開くと、**Then** API Gateway のリクエスト数パネルにデータが表示される
2. **Given** 疑似アラートを複数件 POST した後、**When** Grafana のアラート監視パネルを確認すると、**Then** severity 別のアラート件数が可視化されている
3. **Given** Lambda がエラーを発生させるリクエストを送信した後、**When** Lambda 監視パネルを確認すると、**Then** エラー件数が増加していることが確認できる

---

### User Story 3 - Grafana Alerting による通知条件の確認（Priority: P3）

検証者が Grafana Alerting を使って通知ルールを設定し、条件を満たすデータを送信したときにアラート状態（Firing）になることを確認する。

**Why this priority**: 通知先の実装は任意だが、アラートルールの設定方法を学ぶことは実案件での活用に重要。P1・P2 が完了した後に取り組む。

**Independent Test**: Grafana Alerting でアラートルールを 1 件設定し、条件を満たすデータ送信後に Grafana の Alerting 画面でアラート状態（Firing）になることが確認できれば完了。

**Acceptance Scenarios**:

1. **Given** Grafana Alerting が設定された状態で、**When** Lambda エラーが設定閾値以上発生すると、**Then** Grafana Alerting でアラート状態（Firing）になる
2. **Given** Grafana Alerting が設定された状態で、**When** critical の疑似アラートが設定閾値以上送信されると、**Then** Grafana Alerting でアラート状態（Firing）になる

---

### User Story 4 - 検証後のリソース削除（Priority: P4）

検証終了後、検証者が作成したすべての AWS リソースを削除し、不要な継続課金が発生しないことを確認する。

**Why this priority**: コスト管理のために必須。検証後の後片付けを明示的なユーザーストーリーとして定義する。

**Independent Test**: AWS コンソール上で作成したリソース（API Gateway / Lambda / DynamoDB / CloudWatch Logs グループ / Managed Grafana ワークスペース）が存在しないことを確認できれば完了。

**Acceptance Scenarios**:

1. **Given** 検証が完了した後、**When** 検証者が各 AWS リソースを削除すると、**Then** AWS コンソール上にリソースが存在しなくなる
2. **Given** リソース削除後、**When** AWS Billing を確認すると、**Then** 翌日以降に本システムに起因する継続課金が発生しない

---

### Edge Cases

- 不正な JSON 形式（パース不可）のリクエストボディを POST した場合は HTTP 400 を返す
- JSON ボディが空の場合は HTTP 400 を返す
- occurredAt に ISO 8601 形式以外の文字列が含まれる場合は HTTP 400 を返す
- Lambda がデータストアへの書き込みに失敗した場合は HTTP 500 を返し、エラー内容をログに出力する
- Grafana から CloudWatch へのデータソース接続が失敗した場合、Grafana UI にエラーメッセージが表示される

## Requirements *(mandatory)*

### 9. 機能要件

#### FR-001: 疑似アラート受信機能（必須）

- **FR-001-1**: システムは HTTP POST メソッドで疑似設備アラートを受信できること
- **FR-001-2**: 受信するリクエストボディは JSON 形式であること
- **FR-001-3**: リクエストボディには以下のフィールドを含むこと

  | フィールド名 | 型 | 必須/任意 | 説明 |
  |---|---|---|---|
  | alertId | string | 必須 | アラートの一意識別子 |
  | facilityId | string | 必須 | 設備の識別子 |
  | facilityName | string | 必須 | 設備名 |
  | severity | string | 必須 | 重要度（critical / warning / info） |
  | alertType | string | 必須 | アラート種別 |
  | message | string | 必須 | アラートメッセージ |
  | occurredAt | string | 必須 | アラート発生日時（ISO 8601 形式） |

- **FR-001-4**: severity は "critical" / "warning" / "info" の 3 値のみ受け付けること
- **FR-001-5**: 必須フィールドが欠けている場合は HTTP 400 エラーを返すこと
- **FR-001-6**: severity に不正値が含まれる場合は HTTP 400 エラーを返すこと
- **FR-001-7**: JSON パース不可のボディの場合は HTTP 400 エラーを返すこと
- **FR-001-8**: エラー時のレスポンスボディは構造化 JSON 形式とすること（例: `{"error": "INVALID_SEVERITY", "message": "severity must be one of: critical, warning, info"}`）

#### FR-002: アラート保存機能（必須）

- **FR-002-1**: 受信した疑似アラートをデータストアに保存できること
- **FR-002-2**: 保存時にシステム受信日時（receivedAt）をレコードに自動付与すること
- **FR-002-3**: alertId を主キーとして一意に管理すること
- **FR-002-4**: 同一の alertId が送信された場合は、既存レコードを上書き更新すること（upsert 動作）
- **FR-002-5**: 保存に失敗した場合は HTTP 500 エラーを返すこと

#### FR-003: ログ出力機能（必須）

- **FR-003-1**: 処理開始時にログを出力すること（リクエスト受信・alertId を記録）
- **FR-003-2**: 正常終了時にログを出力すること（保存成功・alertId を記録）
- **FR-003-3**: 異常終了時にログを出力すること（エラー種別・原因を記録）
- **FR-003-4**: 入力チェックエラー時には、どのフィールドがどのように不正であったかを確認できるログを出力すること
- **FR-003-5**: 過剰なログ出力は避けること（デバッグレベルのログは含めない）

#### FR-004: メトリクス可視化機能（必須）

Grafana ダッシュボードで以下を可視化できること：

**API Gateway メトリクス**
- **FR-004-1**: リクエスト数（Count）
- **FR-004-2**: 4xx エラー数（4XXError）
- **FR-004-3**: 5xx エラー数（5XXError）
- **FR-004-4**: レイテンシ（Latency）

**Lambda メトリクス**
- **FR-004-5**: 実行回数（Invocations）
- **FR-004-6**: エラー数（Errors）
- **FR-004-7**: 実行時間（Duration）

**DynamoDB メトリクス**
- **FR-004-8**: 読み込みキャパシティ消費量（ConsumedReadCapacityUnits）
- **FR-004-9**: 書き込みキャパシティ消費量（ConsumedWriteCapacityUnits）
- **FR-004-10**: スロットル発生有無（ThrottledRequests）

**疑似アラートメトリクス（ログクエリ使用）**
- **FR-004-11**: 疑似アラートの総件数
- **FR-004-12**: severity 別のアラート件数（critical / warning / info）

#### FR-005: ダッシュボード機能（必須）

- **FR-005-1**: Grafana 上にダッシュボードを 1 つ以上作成できること
- **FR-005-2**: 最小構成では以下をすべて 1 つのダッシュボードに統合してもよい
  - API Gateway 監視パネル
  - Lambda 監視パネル
  - DynamoDB 監視パネル
  - 疑似アラート件数パネル（severity 別含む）
- **FR-005-4**: ダッシュボード作成後、Grafana の JSON エクスポート機能を使って定義ファイルを保存すること（再現・再利用・将来の IaC 化に備えるため）
- **FR-005-3**: 拡張時は以下のダッシュボードに分割できる設計とすること（任意）
  - システム概要ダッシュボード
  - API 監視ダッシュボード
  - Lambda 監視ダッシュボード
  - DynamoDB 監視ダッシュボード
  - 疑似設備アラート監視ダッシュボード

#### FR-006: Grafana Alerting 検証機能（任意）

- **FR-006-1**: Lambda エラー数が設定閾値以上になった場合にアラート状態（Firing）になる通知ルールを設定できること
- **FR-006-2**: API Gateway 5xx エラーが発生した場合にアラート状態（Firing）になる通知ルールを設定できること
- **FR-006-3**: critical の疑似アラートが設定閾値以上発生した場合にアラート状態（Firing）になる通知ルールを設定できること
- **FR-006-4**: 通知先（メール・Slack 等）の実装は任意とする
- **FR-006-5**: アラートルールが Firing 状態になることを Grafana UI 上で確認できること

### 10. 非機能要件

#### NF-001: コスト（必須）

- **NF-001-1**: Amazon Managed Grafana の費用は約 9 USD 程度を許容する
- **NF-001-2**: API Gateway / Lambda / DynamoDB は AWS 無料枠または最低料金に抑えること
- **NF-001-3**: CloudWatch Logs の保持期間は 7 日間に設定すること
- **NF-001-4**: カスタムメトリクスの作成は最小限に抑えること（標準メトリクスを最大限活用）
- **NF-001-5**: 検証後にすべてのリソースを削除できる構成にすること

#### NF-002: セキュリティ（必須）

- **NF-002-1**: API エンドポイントは HTTPS のみで公開すること
- **NF-002-2**: API 認証機能（API キー・IAM 認証等）は今回の検証スコープ外とする（対象外）
- **NF-002-3**: IAM ロール・ポリシーは最小権限の原則を適用すること
- **NF-002-4**: 処理コンポーネントに付与する IAM ロールには必要最小限の権限（データストア書き込み + ログ出力）のみを付与すること
- **NF-002-5**: Grafana には検証者本人のみアクセスできる設定にすること
- **NF-002-6**: 機密情報・個人情報は一切扱わないこと（疑似データのみ使用）

#### NF-003: 可用性（必須）

- **NF-003-1**: 高可用性構成（マルチ AZ・マルチリージョン）は不要
- **NF-003-2**: 各 AWS マネージドサービスの標準的な可用性（SLA）を利用する
- **NF-003-3**: 個人検証環境のため、ダウンタイムへの対応は不要

#### NF-004: 性能（必須）

- **NF-004-1**: 想定リクエスト数は数十〜数百件程度（高負荷試験は対象外）
- **NF-004-2**: 厳密なレイテンシ目標値は設けない
- **NF-004-3**: 少量の疑似アラートを送信して可視化できればよい

#### NF-005: 運用性（必須）

- **NF-005-1**: リソースの構築・削除が容易な構成にすること
- **NF-005-2**: 後続で IaC（Terraform / CDK 等）に移行しやすい構成にすること
- **NF-005-3**: ログ管理サービスで障害原因を追跡できること
- **NF-005-4**: Grafana 上で主要な稼働状況を確認できること

#### NF-006: 監視性（必須）

- **NF-006-1**: 標準メトリクスを Grafana でリアルタイムに参照できること
- **NF-006-2**: ログを AWS コンソールまたは Grafana から参照できること
- **NF-006-3**: API / 処理コンポーネント / データストアの主要メトリクスを可視化できること
- **NF-006-4**: 疑似アラートの業務イベント件数（総数・severity 別）を可視化できること

#### NF-007: 拡張性（任意）

以下の拡張に対応できる設計余地を残すこと（今回の検証スコープには含めない）：

- 顧客別ダッシュボード
- 設備別ダッシュボード
- インシデント管理機能
- Amazon Bedrock 連携
- 報告書自動作成機能
- 通知機能（メール・Slack 等）
- IaC による環境構築自動化

### 11. データ要件

#### 11.1 アラートレコード

データストアに保存するアラートレコードのデータ構造：

| フィールド名 | 型 | 必須/任意 | 説明 |
|---|---|---|---|

#### 11.2 データ保持ポリシー

- **データストア**: 検証期間中のみ保持。検証後にテーブルごと削除する
- **ログ**: ログ保持期間は 7 日間に設定する
- **標準メトリクス**: AWS の標準メトリクスのデフォルト保持期間に準拠する（追加設定不要）

#### 11.3 データ量

- 送信件数は数十〜数百件程度（検証目的の最小量）
- すべて疑似データを使用する（実データ・個人情報は扱わない）

#### 11.4 Key Entities *(include if feature involves data)*

- **Alert（疑似アラートレコード）**: 設備から発生した疑似アラートの情報。alertId を一意識別子として管理。severity（重要度）・facilityId（設備 ID）・occurredAt（発生日時）が可視化・集計のキー属性となる
- **receivedAt（受信日時）**: 処理コンポーネントがリクエスト受信時に自動付与するシステムタイムスタンプ。アラート発生時刻（occurredAt）と受信時刻の差分を確認できる

## Assumptions

- **重複 alertId の扱い**: 同一 alertId の再送信は upsert（上書き更新）として処理する。既存データは保持しない
- **API 認証**: 今回は検証用途のため API 認証を設けない。URL が分かれば誰でも POST できる設計とする（URL は非公開で管理する）
- **Grafana ユーザー管理**: Grafana の管理者ユーザーは検証者のみとする。認証方式は **Grafana 組み込み認証（username / password）** を使用する。IAM Identity Center は使用しない
- **データストア設計**: 単一テーブル設計で alertId をパーティションキーとする。ソートキーは不要
- **処理コンポーネントのランタイム**: 実装言語は後続の仕様書で決定する（Python または Node.js を想定）
- **ログクエリによるアラート件数集計**: severity 別集計はログクエリ機能を使用するが、標準メトリクスではないため Grafana の CloudWatch データソース設定でログクエリを有効化する必要がある
- **occurredAt フォーマット**: ISO 8601 形式（例: 2026-04-25T10:00:00Z）を前提とする
- **疑似アラートデータ**: 実際の設備データは使用せず、テスト用に作成した JSON データを手動または簡易スクリプトで送信する
